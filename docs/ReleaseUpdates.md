# Verified Updates

The owner confirmed that no release-signing public pin or trusted Windows
code-signing provider has been approved. Production updater activation and
trusted publisher acceptance are therefore **BLOCKED**. No replacement key,
self-signed certificate, update URL, or production trust file is generated.

## Implemented Boundary

`scripts/release_update.py` validates and prepares updates for the existing
native Windows installer. `UpdateManager` connects this pipeline to Settings /
About. It uses the packaged Python runtime, not a developer PATH interpreter.
No owner trust file or update endpoint is shipped or generated automatically.

The pipeline validates an authority-signed release manifest, then copies and
hashes a bounded installer into an isolated candidate directory. Windows
Authenticode verification must also succeed for the separately pinned publisher
and a timestamp. Only after all gates pass does it atomically persist the
high-water record and pending-restart record. The installed browser is untouched.

The implementation uses cryptography's Ed25519 verifier, SHA-256, and the Windows
trust provider. No cryptographic primitive is implemented locally. The tests
generate only disposable signing fixtures, never production authorities.

## Owner Trust Input

A future owner-approved local trust file has exactly these fields:

- `version`: integer 1.
- `manifestPublicKey`: the approved 32-byte Ed25519 public key, unpadded base64url.
- `windowsCertificateSha1`: the approved certificate's 40-hex public thumbprint.

The certificate thumbprint is an identifier, not the artifact digest algorithm.
It does not replace Windows chain/revocation verification. Bootstrap/config
authorities are not automatically reused for signing software releases.

## Release Manifest

The signed JSON document has exactly these fields:

| Field | Meaning |
| --- | --- |
| version | Integer 1 |
| sequence | Monotonic integer 1 through 2^63-1 |
| productVersion | Three nonnegative decimal components, no prerelease suffix |
| platform | `windows-x64`; other platforms currently rejected |
| issuedAt / expiresAt | Unix seconds, current validity, at most 31 days |
| artifact | Exactly `GrangerSetup.exe` |
| size | Exact byte count, at most 2 GiB |
| sha256 | Lowercase 64-hex digest of the final signed installer |
| windowsCertificateSha1 | Must equal the owner trust input |
| releaseNotes | At most 8192 characters; must be escaped when displayed |
| signature | 64-byte Ed25519 signature, unpadded base64url |

Signing bytes are `Granger Browser release manifest v1\0` followed by the
unsigned document encoded as ASCII JSON with sorted keys, ASCII escapes,
separators `,` and `:`, and no whitespace. `signature` is omitted from the signed
object. The owner must provide an approved signing provider; this tool has no
private-key input or signing operation. Duplicate JSON keys are rejected.

## Consent and Persistence

Missing policy means `ask`. Selecting `auto` requires an explicit local
`--user-consent` action. The manifest cannot change policy. `prepare` requires
per-update `--user-approved` or previously recorded opt-in. Revocation or trust
changes during copying/verification cancel activation. A policy lock serializes
the final consent check and pending write; the main preparation lock is
OS-owned, released automatically on process death.

Even auto preparation ends at `AWAITING_RESTART_CONSENT`. Later cancels active
work without scheduling installation. A separate restart confirmation starts
the apply helper; automatic preparation does not imply automatic execution.
The helper waits for browser exit and revalidates the signed manifest, file
hash, platform/version, high-water, trust and policy. A Windows read handle
denies artifact writes/replacement across final verification and process launch.
The existing offline installer owns atomic installation and rollback. Browser
self-apply is restricted to the normal installed Windows location; portable
copies and Linux self-apply are not supported by this Windows installer flow.

Prepared state consists of policy, high-water, a bounded pending record, the
verified installer, and the signed manifest. At most two installer candidates
are retained; further distinct candidates are rejected until explicit cleanup.
No existing installation or last-known-good browser is deleted. An interruption
after high-water and before pending can retry the exact same generation. A
pending record alone is never authorization to execute.

## Browser Downloads

The owner-provisioned public trust file belongs at `runtime/updater/trust.json`
relative to the executable. A separate `runtime/updater/source.json` contains
`manifestUrl`, an HTTPS URL. The installer is resolved as `GrangerSetup.exe`
in that URL's directory. Neither file is generated by the browser. Only public
trust identifiers belong in these files, never signing credentials.

The browser validates the local trust schema before fetching metadata, then
verifies its signature before downloading an installer. Requests require the
existing application-wide loopback SOCKS/HTTP privacy gateway, never NoProxy or
system proxy fallback. Cookies and redirects are disabled. The endpoint must
serve the files directly; redirecting release/CDN endpoints are not supported.
Metadata is bounded to 64 KiB and artifacts to the signed size (maximum 2 GiB).
QSaveFile keeps partial downloads from replacing complete files. Cancellation
invalidates callbacks and terminates verification work; there is no idle poll.

Settings exposes current/available versions, escaped release notes, Check,
Update now, Later, restart confirmation and persistent Ask/Auto preparation.
Auto opt-in requires an explicit native confirmation and can be revoked.
Production signature, publisher, download and installed-apply acceptance remain
BLOCKED until the owner supplies approved public signing identifiers/provider.

## Local Commands

Use only a disposable candidate state directory during development:

```powershell
python scripts/release_update.py --state-dir output/update-candidate status
python scripts/release_update.py --state-dir output/update-candidate policy auto --user-consent
python scripts/release_update.py --state-dir output/update-candidate policy ask
python scripts/release_update.py --state-dir output/update-candidate prepare --manifest <signed-manifest.json> --artifact <GrangerSetup.exe> --trust <owner-public-trust.json> --current-version 0.4.4 --user-approved
python -m unittest discover -s scripts/tests -p test_release_update.py -v
```

No production trust file is included, so preparation cannot pass production
verification today. Filesystem UNC paths and symlinks/junctions are rejected.
The preparation gate accepts a verified installer, not an arbitrary ZIP extractor.

## Windows Trust and Privacy

`windows_artifact_trust.py` invokes WinVerifyTrust with cache-only URL retrieval,
chain revocation checks excluding the root, obsolete-digest rejection, no trust
UI, and Internet-origin policy. Signer/timestamp identities are read from that
verified provider state, not by launching a second verifier that might retrieve
certificate data over the network. Insufficient cached revocation evidence
fails closed; it does not disable revocation or request data directly.

The official installed Python executable passed this offline verifier in the
local test. Unsigned fixtures were rejected. This is not evidence that a Granger
release is signed, or that its SmartScreen reputation is established.
